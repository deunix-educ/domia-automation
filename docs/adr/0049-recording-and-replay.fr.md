# 0049 — Enregistrement des caméras, archive ReductStore et replay


- Statut : accepté
- Date : 2026-11-08

## Contexte
la référence fait enregistrer MediaMTX (`record: true` sur le *path* des caméras en mode continu ou mouvement, ou après un démarrage manuel), scanne `/recordings` toutes les 60 s (une tâche un planificateur externe), crée un `Recording` par segment, pousse le fichier entier dans le bucket ReductStore `surveillance` (entrée `cam_<uuid>`, étiquettes `event_type`, `camera_name` en ASCII, `camera_uuid`, quota FIFO de 50 Go) et sert le fichier local, à défaut ReductStore. Le fichier local n'est **jamais supprimé** (le volume grossit sans limite) et le dernier fichier de chaque caméra est toujours ignoré. Plan R6 : D10, critère « 1 h d'enregistrement continu sans perte de segment ».

## Décision
- **MediaMTX enregistre, DomiNet n'écrit aucune vidéo.** `PathConf` porte déjà `record` (continu et mouvement : vrai, comme la référence) ; le format (`fmp4`), le chemin (`/recordings/%path/%Y-%m-%d_%H-%M-%S-%f`), la durée de segment et la partie (`1s`) sont la configuration **globale** de MediaMTX (dev : `deploy/mediamtx/mediamtx.dev.yml`, 10 s ; production : 60 s, générée au lot R7).
- **Scan** (`dominet_surveillance::recording`) : un segment est **terminé** quand son fichier n'a plus été modifié depuis `RECORDINGS_GRACE_SECS` (15 s, comme la référence). Écart voulu : la référence ignorait toujours le dernier fichier, si bien que le dernier segment d'une caméra dont l'enregistrement s'arrête n'était jamais pris ; ici la date de modification suffit, tous les segments le sont. Date de début lue dans le nom (`%f` de MediaMTX = microsecondes ; chrono lirait des nanosecondes, la lecture est faite à la main), à défaut la date de modification.
- **Rôle `video`** (`dominet_server::recordings`) : toutes les `RECORDINGS_SCAN_SECS` — indexe les segments terminés des caméras **actives qui enregistrent** (mode ≠ `none`, comme la référence), puis archive. Type du segment : `manual` en mode manuel, `motion` si un mouvement tombe dans sa fenêtre (`RECORDINGS_SEGMENT_DURATION`), sinon `continuous` (règle de la référence). Un segment déjà indexé (chemin unique en base) ne l'est jamais deux fois.
- **Archive** (`dominet_store::video::ReductVideo`) : bucket `surveillance` (`REDUCTSTORE_VIDEO_BUCKET`), entrée `cam_<uuid>`, horodatage en microsecondes (= `reduct_ts`), étiquettes de la référence (NFKD puis ASCII pour `camera_name`), quota FIFO `VIDEO_QUOTA_GB` à la création du bucket. **Écart voulu (D10) : le fichier local est supprimé après un push réussi**, le volume ne grossit plus. Un push qui échoue (ReductStore en panne) note l'erreur sur le segment (`status = error`), garde le fichier et **réessaie à chaque passage** ; sans `REDUCTSTORE_URL` les segments restent sur le disque (`pending`) et sont servis depuis lui.
- **Replay** : `GET /surveillance/recordings/<uuid>/<id>/stream/` (route de la référence, tout compte connecté). Fichier local s'il existe encore (`tower_http::ServeFile` : `Range`, seek natif), sinon le segment est lu dans ReductStore et servi **avec le même support de `Range`** (206, `Content-Range`, 416). Un chemin en base hors de `RECORDINGS_DIR` n'est jamais servi. Page `/surveillance/recordings/<uuid>` : un jour à la fois (fuseau du serveur, heures locales), lecteur `<video>` natif, précédent / suivant ; **suppression : administrateurs** (fichier, entrée ReductStore, ligne).
- **Enregistrement manuel** : `PATCH /v3/config/paths/patch/<uuid>` `{"record": bool}` (`MediaMtx::set_record`), bouton Démarrer / Arrêter de la page des enregistrements (administrateurs, caméra en mode manuel seulement). Une resynchronisation complète de MediaMTX (démarrage, bouton « Synchroniser ») remet le path à son état de base — donc **arrête** un enregistrement manuel en cours ; la référence avait le même effet via son YAML.
- **Caméra supprimée** : son dossier de segments est supprimé avec elle, après l'arrêt de son *path* (la référence laissait les fichiers).
- **Sécurité** : les chemins servis ou supprimés doivent être sous `RECORDINGS_DIR` sans `..` ; les identifiants de dossier sont des UUID de caméra connus.

## Vérification
- Unitaires : lecture des noms de segments (avec / sans fraction, microsecondes), segments refroidis seulement, dernier segment d'une caméra arrêtée pris, nom illisible, plages `Range` (début, fin, suffixe, hors limites), jours précédent / suivant (années bissextiles).
- Intégration (vrai ReductStore de la stack de dev, bucket jetable, vraie base) : indexation par mode, type `motion` / `continuous` / `manual`, push, **fichier local supprimé**, relecture depuis ReductStore avec les étiquettes exactes, aucun doublon au passage suivant, suppression ; ReductStore en panne puis revenu (fichier gardé, erreur notée, repris) ; sans archive ; chemin hors dossier refusé ; enregistrement manuel (faux MediaMTX, refus hors mode manuel).
- E2E (`tests/e2e/recordings.py`, vrai flux H.264 → MediaMTX de dev → ReductStore) : le path enregistre, segments archivés, 200 / 206 / 404, signature MP4, taille conforme à l'index, page, lecteur, mode manuel (démarrage et arrêt, segment `manual`), suppression.
- **Endurance** (`tests/e2e/recordings_soak.py`, `SOAK_SECONDS=3600 tools/e2e.sh recordings_soak`) : une heure de flux continu, aucun trou entre segments consécutifs, aucun en erreur, durée cumulée ≥ 97 % de la durée publiée, tous relus depuis ReductStore. **Résultat (2026-11-08, poste de dev, pendant un `make ci` complet) : 3 600 s de flux continu, les 7 vérifications passent** (aucun trou, aucun segment en erreur, tous relus depuis ReductStore). Les chiffres détaillés (nombre de segments, plus grand écart) sont imprimés par le script mais `tools/e2e.sh` ne les affiche pas ; à relever dans la synthèse de R6.

## Limites
- Pas de frise chronologique de 24 h (la référence en dessinait une) : liste + lecteur. Reportable.
- Le mode `motion` enregistre en continu comme la référence (le type seul distingue les segments avec mouvement) ; un enregistrement déclenché par le mouvement serait un changement de comportement, à décider avec le lot 8.
- Le volume `/recordings` doit être commun à MediaMTX et au rôle `video`, et accessible en écriture au second (suppression). En dev, MediaMTX tourne sous l'identifiant de l'utilisateur (`DEV_UID`) pour que les fichiers lui appartiennent.
