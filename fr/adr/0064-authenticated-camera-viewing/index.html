    ADR 0064 — Visionnage des caméras authentifié : MediaMTX interroge DomiNet, jetons de visionnage par compte et identifiants de flux personnels¶

    Statut : implémenté (2026-11-24, lots 1 à 5 ; accepté le même jour par le propriétaire). Les écarts entre ce texte et ce qui a été construit sont dans Tel que construit. Clôt le point « identifiants de caméra par spectateur » de la feuille de route et de À améliorer.

    Contexte¶

    Aujourd'hui, toute personne connectée au réseau domestique peut regarder toutes les caméras : MediaMTX autorise read et playback à tout le monde (authInternalUsers, user: any, sans mot de passe), en RTSP (8554) et en WebRTC (8189, et WHEP par nginx sur /webrtc/). Seuls la publication, l'API et les métriques sont réservées au réseau Docker et à la machine. L'interface, elle, est protégée par des comptes (tout compte connecté peut regarder) : la vidéo est donc le seul endroit où le système de comptes ne s'applique pas. Sécurité documente cet écart et conseille de mettre les invités sur un autre réseau.

    Ce que le propriétaire a décidé (2026-11-23) : l'authentification est déléguée à DomiNet, tout compte connecté peut regarder toutes les caméras (pas de droits par caméra), et chaque compte peut obtenir des identifiants personnels et révocables pour les lecteurs externes (VLC, applications du téléphone).

    Ce que dit la documentation de MediaMTX (lue le 2026-11-23 ; la page n'est pas versionnée et est probablement plus récente que la 1.21.3, donc les points ont été vérifiés d'abord sur le vrai binaire 1.21.3) : - authMethod: http avec authHTTPAddress : MediaMTX envoie en POST {user, password, token, ip, action, path, protocol, id, query} ; un statut 20x autorise, tout autre refuse. Un corps optionnel {"expireAt": "<RFC 3339>"} ferme la session à cette date. - Les clients RTSP envoient d'abord des identifiants vides ; le serveur doit répondre 401 pour qu'ils les envoient. Les navigateurs et clients WHEP peuvent envoyer Authorization: Basic … ou Authorization: Bearer <jeton>. - authHTTPExclude évite l'appel HTTP pour certaines actions (api, metrics, pprof par défaut). Vérifié sur la 1.21.3 (lot 0) : publish peut être exclu (authHTTPExclude: [{action: publish}] ; la liste n'accepte pas de champ ips, l'exclusion vaut donc pour toute adresse, sans danger puisque le port de publication n'est joignable que depuis le réseau Docker) ; authInternalUsers est ignoré avec authMethod: http (même les appels api passent par l'appel HTTP et sont refusés si DomiNet est arrêté, sauf exclusion) ; un jeton Bearer seul arrive dans token (ni user ni password) ; avec Basic, le mot de passe arrive dans password et est recopié dans token ; un ?token= dans l'URL WHEP n'est pas lu comme jeton (il n'apparaît que dans query). - Aucune mise en cache des décisions n'est documentée : un appel HTTP par authentification, au moins deux pour une session RTSP.

    Options¶

    • A. MediaMTX interroge DomiNet (authMethod: http) (choisie). Un seul endroit décide, les comptes et la révocation sont ceux de l'application, le navigateur et les lecteurs externes sont couverts.
    • B. auth_request de nginx sur /webrtc/ seulement. Simple, mais RTSP (8554) et ICE (8189) restent ouverts sur le LAN : la moitié de l'écart demeure.
    • C. Un mot de passe de lecture partagé dans la configuration de MediaMTX. Trivial, mais pas « par spectateur » : impossible de couper une personne sans le changer pour tous.
    • D. Un utilisateur interne MediaMTX par spectateur, écrit dans le fichier de configuration. Demande une réécriture et un rechargement à chaque changement, et duplique la base des comptes.

    Décision¶

    Option A. - MediaMTX tourne avec authMethod: http et authHTTPAddress: http://dominet:8000/internal/mediamtx/auth. La route n'existe que côté réseau Docker : nginx ne la relaie pas, et le gestionnaire refuse tout appelant hors du réseau Docker. - Exclus de l'appel HTTP : api, metrics et pprof (authHTTPExclude), et seulement eux. DomiNet appelle l'API pendant son démarrage, avant de pouvoir répondre, et Prometheus doit continuer à collecter quand DomiNet est arrêté ; leurs ports (9997, 9998) ne sont pas publiés sur la machine. publish n'est pas exclu, bien qu'il le puisse : l'exclusion n'a pas de filtre d'adresse, elle ouvrirait la publication à tout le réseau local (le RTSP 8554 est publié). Le gestionnaire le décide, depuis une adresse privée seulement (les caméras sont tirées, personne ne publie sauf la fausse caméra de la démo). - La décision (gestionnaire POST) n'autorise un read / playback sur un path de caméra que pour un identifiant valide d'un compte actif ; publish ne vient que d'une adresse privée ; des identifiants vides reçoivent 401 (le défi RTSP) ; tout le reste est refusé. Un refus est compté dans une métrique et journalisé sans aucun secret. Les échecs Basic comptent dans le même blocage que la connexion (ADR 0004). - Navigateur : à l'ouverture de la page live, une fonction serveur (session exigée) crée un jeton de visionnage : 256 bits aléatoires, stocké haché (SHA-256), lié au compte, valable quelques minutes. Le client WHEP l'envoie en Authorization: Bearer ; le gestionnaire le lit dans token (jamais dans query). Il est renouvelé avant son expiration. - Lecteurs externes : une page de compte (« Mon compte » → « Accès aux caméras ») crée un identifiant de flux personnel : le nom d'utilisateur du compte et un mot de passe généré montré une seule fois, stocké haché, révocable, avec une date de dernier usage. La page affiche l'adresse RTSP à coller dans VLC. Un compte peut en avoir plusieurs (un par appareil). - Même modèle de stockage que les jetons MCP (ADR 0059) : table avec empreinte, propriétaire, nature, dates de création et d'expiration, date de révocation. Aucune clé de signature à gérer (le réglage SECRET_KEY a été supprimé). - Les lectures de DomiNet lui-même (le rôle video décode le re-stream de MediaMTX) utilisent un identifiant de service généré par make prod-init (MEDIAMTX_READ_USER, MEDIAMTX_READ_PASSWORD), pas une exception par adresse IP. Faire confiance à la plage du réseau Docker pour read serait faux : selon le mode du proxy Docker, le trafic du LAN peut sembler venir de l'adresse du pont. - Révocation : effective à la connexion suivante. Pour une session ouverte, DomiNet la coupe par l'API de MediaMTX (/v3/*conns/kick, /v3/webrtcsessions/kick), à l'aide de l'id de session que MediaMTX envoie dans l'appel d'authentification (vérifié : c'est l'identifiant de session de l'API, pas celui de l'en-tête WHEP Location ; en RTSP, rtspsessions et non rtspconns). expireAt (vérifié) borne aussi une session ; c'est le recours.

    Conséquences¶

    • Changement incompatible pour les spectateurs : VLC et les applications du téléphone devront recevoir un identifiant personnel avant de pouvoir regarder. La note de version et Sécurité le disent, avec les étapes de migration.
    • DomiNet devient une dépendance du visionnage. S'il est arrêté, MediaMTX refuse les lectures (échec fermé). L'enregistrement n'est pas touché : les caméras sont tirées par MediaMTX et écrites par l'enregistreur à l'intérieur du réseau Docker.
    • Un appel HTTP de plus par session (deux en RTSP) ; négligeable à cette échelle.
    • Le plan média (ICE, 8189) n'est pas authentifié en soi : une session WebRTC est autorisée au moment où l'offre WHEP est postée. Rediriger 8189 ou 8554 vers Internet reste déconseillé.
    • Hors périmètre : droits par caméra, authentification Digest, HLS (désactivé), chiffrement de bout en bout du RTSP.

    Plan (un lot à la fois, chacun validé avant le suivant)¶

    1. Test sur MediaMTX 1.21.3 : fait le 2026-11-24 avec un serveur d'authentification jetable, ffmpeg et curl. Restent à essayer VLC (lot 2) et un vrai navigateur (lot 3).
    2. Table, migration et règles du domaine (jetons, identifiants, expiration), avec tests.
    3. Route d'authentification (2a, faite), puis son câblage (2b) : configuration de MediaMTX (production et démo ; la pile de dev reste ouverte jusqu'au lot 3, qui en a besoin pour tester le navigateur), identifiant de service, scripts d'installation et de migration, nginx.
    4. Parcours navigateur : jeton de visionnage et client WHEP, test de bout en bout sur la page live.
    5. Page « Accès aux caméras », révocation et coupure des sessions.
    6. Documentation (EN et FR), note de version, retrait des entrées de la feuille de route et de « À améliorer ».

    Tel que construit (2026-11-24)¶

    • Jeton du navigateur : la page demande un nouveau jeton de visionnage à chaque connexion (reconnexions comprises) au lieu de le renouveler en arrière-plan : MediaMTX ne le vérifie qu'au moment où l'offre WHEP est postée, et une session en cours n'est pas coupée à son expiration. La fermeture d'une session (DELETE) n'est pas authentifiée par MediaMTX (vérifié) : la page ne garde donc pas le jeton.
    • Révocation : les sessions ouvertes sont retrouvées par le nom d'utilisateur que MediaMTX enregistre (GET /v3/{rtsp,webrtc}sessions/list, puis kick/<id>), et non par l'id de l'appel d'authentification. C'est sans état et cela survit à un redémarrage de DomiNet, mais cela ne distingue pas deux identifiants du même compte : révoquer l'un ferme les sessions du compte, et un appareil muni d'un autre mot de passe se reconnecte. Une session du navigateur ouverte avec un jeton de visionnage n'a pas de nom d'utilisateur et n'est pas fermée. Si MediaMTX est injoignable, la révocation tient quand même (refus à la connexion suivante, expireAt pour une session restée ouverte).
    • expireAt : renvoyé pour un identifiant personnel (la session s'arrête avec l'identifiant) et jamais pour un jeton de visionnage.
    • Blocage : seuls les échecs avec un nom d'utilisateur comptent ; la première requête vide d'un client RTSP ne compte pas. Les réussites ne sont pas enregistrées (une ligne par session RTSP remplirait la table).
    • Non exclu de l'appel HTTP : publish (voir Décision). Exclus : api, metrics, pprof.
    • Pile de développement : son MediaMTX reste ouvert (il tourne dans Docker, DomiNet sur la machine). Le comportement authentifié est couvert par tools/e2e.sh live_auth (navigateur, MediaMTX jetable avec la configuration livrée) et par le test ignoré real_mediamtx_auth (RTSP, WHEP, coupure de session sur un vrai MediaMTX 1.21.3).
    • Non fait : la fermeture des sessions d'un compte désactivé ou supprimé ; un journal d'audit des créations et révocations d'identifiants (elles sont journalisées, sans le secret) ; le port RTSP affiché par la page est celui de la production (8554), celui de la démo est 8555.
    • Vrais lecteurs : ffplay lit avec un identifiant personnel. Le paquet VLC de Debian 13 ne sait lire aucun flux RTSP (compilé sans live555 ; reproduit sans authentification) : VLC n'a donc pas pu servir de test. Les applications du téléphone et VLC en Flatpak n'ont pas été essayés.
